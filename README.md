# Convert Strategy to Speaker Script

将战略方案、品牌方案、营销提案或商业计划，深度分析并转化为一份能够跟随原方案现场展示、可直接朗读的顾问式销售 Word 口播稿。

> 核心原则：不是把方案内容重新念一遍，而是帮助提案人把问题讲透、把价值讲清，并推动客户表达真实业务瓶颈与下一步行动意愿。

当前版本：`v0.1.0`

---

## 1. Skill 简介

`convert-strategy-to-speaker-script` 是一个面向战略咨询、品牌营销、GTM、年度规划和商业提案场景的 Codex Skill。

它能够读取完整方案，提炼各章节的核心洞察，识别数据与逻辑风险，并保持原方案展示顺序，将内容转化为：

- 可跟随方案逐页或逐章节朗读的现场口播稿；
- 具有咨询顾问逻辑的结论先行表达；
- 包含 Insight、比喻、尖锐观点和管理层含义的说服性叙事；
- 能够持续邀请客户参与诊断的顾问式追问；
- 从问题共识自然推进到 MVP、试点或合作下一步的销售收网；
- 经过结构化排版、可直接下载和使用的 Word 文档。

默认适用于约 `80–100 分钟`的完整战略提案，也可以根据用户指定时长压缩或扩展。

---

## 2. 适用场景

当用户提供以下材料并要求生成讲稿时，建议调用本 Skill：

- 海外品牌战略或品牌升级方案；
- 数字营销、社媒、内容或媒介推广方案；
- GTM、市场进入与业务增长方案；
- 年度营销规划、IMC 或整合传播方案；
- 咨询项目、董事会汇报或管理层决策方案；
- 招投标提案、客户比稿或商务合作方案；
- 商业计划书、融资方案或战略路线图；
- 需要从“方案解读”升级为“顾问式销售提案”的其他材料。

支持的常见输入形式取决于运行环境，一般包括：

- `.docx`
- `.pdf`
- `.pptx`
- Markdown 或纯文本
- 已粘贴在对话中的长篇方案内容

典型触发表达：

- “把这份方案生成一份现场提案口播稿。”
- “跟随 PPT 顺序，写一份我可以直接读的讲稿。”
- “用顾问式销售方法讲这份品牌方案。”
- “提炼每个章节的 Insight，并在最后完成销售收网。”
- “沿用之前相同的方法，把新方案转成 Word 口播稿。”

## 3. 核心能力

### 3.1 全文深度分析

不会只读取目录或标题，而是检查：

- 战略诊断与核心矛盾；
- 市场、竞品、客户与决策链；
- 品牌定位、USP、价值体系与信息架构；
- 内容、渠道、媒介与执行节奏；
- Roadmap、预算、KPI 与双方协作；
- 表格、附录、备注和隐藏在细节中的商业假设。

### 3.2 证据分层

重要内容会按以下逻辑处理：

| 类型 | 定义 | 现场表达方式 |
|---|---|---|
| Fact | 方案明确给出的事实或审计数据 | 保留来源、时间和限定条件 |
| Inference | 从事实中推导出的策略判断 | 使用“这意味着”“我们的判断是” |
| Recommendation | 对未来行动的建议 | 使用“建议”“优先”“可以验证” |
| Assumption | 尚未核实的市场或商业假设 | 放入会前核验，不作为确定事实承诺 |

### 3.3 顾问式销售叙事

采用七阶段提案路径：

1. 建立共同目标；
2. 重构客户问题；
3. 用证据完成诊断；
4. 放大不行动的代价；
5. 共创增长标准；
6. 用 MVP 或阶段方案降低风险；
7. 引导客户做出下一步行动承诺。

### 3.4 跟随原方案展示

默认保留原方案章节与节点顺序，不另起一套脱离 PPT 的故事线。

每个主要节点统一包含：

- 对应展示内容；
- 核心 Insight；
- 可直接朗读的主稿；
- 顾问式追问或确认；
- 承上启下的转场；
- 必要时增加主持提示。

### 3.5 销售收网

结尾不会直接跳到“是否签约”，而是通过承诺阶梯推进：

1. 让客户用自己的语言确认问题；
2. 确认维持现状的业务代价；
3. 确认优先市场、产品或客户；
4. 确认试点假设与成功标准；
5. 确认客户侧 Owner 与必要输入；
6. 确认下一次工作坊或启动会日期。

### 3.6 Word 自动生成

内置通用 DOCX 生成脚本，可创建：

- 专业封面；
- 原生 Word 标题层级；
- 页眉和页码；
- 原生编号与项目符号；
- Insight 提示框；
- 规范表格；
- 适合现场读稿的段落节奏与留白。

## 4. 输出结构

默认输出文档包含七个部分：

```text
一、提案人的顾问式销售主线
二、全案核心洞察地图
三、逐页/逐章节现场提案口播稿
四、销售收网与分支追问
五、现场异议处理话术
六、会前必须统一的数据与口径
七、提案人一页速记
```

其中，第三部分严格跟随原方案的 Part、章节或页面节点。

## 7. 使用方式

### 7.1 显式调用

上传或指定方案文件后输入：

```text
使用 $convert-strategy-to-speaker-script，深度分析这份方案，
按照原方案顺序生成一份可直接朗读的顾问式销售现场口播稿，
最终交付可下载的 Word 版本。
```

### 7.2 指定提案时间

```text
使用 $convert-strategy-to-speaker-script，
将附件转为一份 60 分钟现场提案口播稿。
保留所有关键洞察，但压缩执行细节。
```

### 7.3 强化董事会表达

```text
使用 $convert-strategy-to-speaker-script，
面向董事长和管理层重写口播稿。
结论先行、逻辑克制，每个 Part 增加一个具有决策启发的 Insight。
```

### 7.4 强化商务收网

```text
使用 $convert-strategy-to-speaker-script，
重点加强最后 15 分钟的顾问式提问、异议处理和销售收网，
推动客户明确业务瓶颈、MVP 范围、项目 Owner 和下一次会议时间。
```

### 7.5 只生成部分章节

```text
使用 $convert-strategy-to-speaker-script，
先输出 Part 0–Part 2 的口播稿供我确认风格，
确认后再继续其他部分。
```

## 8. Word 生成脚本

### 8.1 运行依赖

建议使用 Python 3.10 或更高版本。

```bash
python3 -m pip install python-docx lxml
```

如需执行 DOCX 逐页渲染检查，还应安装：

- LibreOffice / `soffice`
- Poppler / `pdftoppm`

### 8.2 命令示例

先根据 `assets/speaker-script-outline.md` 生成完整的 Markdown 口播稿，再运行：

```bash
python3 scripts/build_speaker_docx.py \
  --input speaker-script.md \
  --output speaker-script.docx \
  --title "2026–2027 海外品牌战略方案" \
  --subtitle "现场提案口播稿 · 顾问式销售版" \
  --client "CLIENT NAME" \
  --agency "AGENCY NAME" \
  --duration "85–100 分钟"
```

### 8.3 参数说明

| 参数 | 是否必须 | 说明 |
|---|---:|---|
| `--input` | 是 | UTF-8 Markdown 口播稿路径 |
| `--output` | 是 | 输出 `.docx` 路径 |
| `--title` | 是 | Word 封面主标题 |
| `--subtitle` | 否 | 封面副标题 |
| `--client` | 否 | 客户或项目名称 |
| `--agency` | 否 | 提案方名称 |
| `--duration` | 否 | 建议提案时长 |

### 8.4 支持的 Markdown 结构

生成脚本当前支持：

- 一级至三级标题；
- 普通段落；
- `**粗体**`；
- `>` Insight 提示框；
- 有序列表；
- 无序列表；
- GitHub 风格简单表格；
- `---` 内容分隔符。

## 9. 分析与写作标准

### 9.1 不做简单摘要

每个章节必须回答：

1. 表面问题是什么？
2. 结构性原因是什么？
3. 对业务增长有什么后果？
4. 管理层需要做什么选择？
5. 哪些证据可以降低不确定性？

### 9.2 Insight 必须有管理含义

有效 Insight 至少应完成一项任务：

- 揭示隐藏的商业后果；
- 把战术症状重构为战略问题；
- 解释一个关键机制；
- 明确资源取舍；
- 将营销动作连接到增长、风险或销售效率。

不应只是换一种方式重复页面标题。

### 9.3 口播语言标准

- 短段落，适合呼吸和停顿；
- 先讲结论，再解释证据；
- 用“这意味着”“更深一层的问题是”等路标帮助听众理解；
- 比喻用于解释机制，不为了炫技；
- 尖锐观点局部使用，整体保持专业克制；
- 不将未经核验的数据说成确定事实；
- 不使用空泛的“赋能、闭环、抓手”堆叠表达。

## 11. 数据与商业风险控制

以下情况必须进入“会前必须统一的数据与口径”：

- 当前基线高于未来目标；
- 预算明细与总额不一致；
- 同一 KPI 在不同章节出现不同目标；
- 月度目标与年度目标无法对应；
- 阶段命名、日期或展会时间冲突；
- 服务费、媒体费、制作费或税费边界不清；
- MQL、SQL、有效询盘和销售接受率没有定义；
- 使用“唯一、第一、全球领先”但缺少证据；
- 市场规模、增长率和买家行为数据缺少来源或年份；
- 竞品广告预算估算被表述成官方信息。

一场高层提案的可信度，往往不是被战略方向击穿，而是被一个无法解释的数字击穿。

## 13. 版本迭代建议

建议采用 [Semantic Versioning](https://semver.org/)：

```text
MAJOR.MINOR.PATCH
```

- `PATCH`：修复脚本、错别字、格式或小型规则问题；
- `MINOR`：增加新输出模块、新销售框架或新的 DOCX 能力，且保持兼容；
- `MAJOR`：修改核心工作流、目录结构或产生不兼容变化。

推荐发布流程：

1. 从 `main` 创建功能分支；
2. 更新 Skill、引用文件或脚本；
3. 使用至少一份真实方案进行回归测试；
4. 验证 Skill 结构；
5. 生成并检查测试 Word；
6. 合并到 `main`；
7. 创建 Git Tag，例如 `v0.2.0`；
8. 在 GitHub Release 中说明新增能力、修复内容和兼容性影响。

建议的分支命名：

```text
feature/add-short-pitch-mode
feature/add-bilingual-output
fix/docx-table-width
docs/update-usage-examples
```

建议每次迭代至少验证三个维度：

- **内容覆盖率**：是否遗漏方案主要节点；
- **销售有效性**：问题是否能推动客户表达真实瓶颈；
- **文档质量**：Word 是否可读、可打印、无布局缺陷。

## 15. 已知限制

- 输入方案质量会直接影响结论质量；缺少事实或数据时，Skill 只能提出假设与核验问题。
- 无法替代客户内部对技术、案例、预算与商业承诺的最终确认。
- 高客单价 B2B 成交受产品、价格、交付、销售响应和市场周期共同影响，不应承诺无条件成交结果。
- DOCX 渲染结果可能因本机字体和 LibreOffice/Word 版本不同而略有差异。
- 当前 Word 生成脚本主要面向中文提案稿；复杂多语言排版需要进一步适配。
